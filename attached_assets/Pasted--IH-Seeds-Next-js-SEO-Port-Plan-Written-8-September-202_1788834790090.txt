# IH Seeds — Next.js SEO Port Plan

**Written:** 8 September 2026
**Goal:** Serve the existing public website as server-rendered HTML so search engines and AI crawlers can read it, with the design pixel-identical and the backend untouched.
**Constraint:** Do not re-code, re-design or re-test the backend, the admin, or the design.

---

## 0. What is and is not changing

**Changing — one thing only:** how the public HTML is produced. Today the browser downloads an empty `<div id="root">` and JavaScript builds the page afterwards. After this port, the server sends the finished HTML.

**Not changing:**

| Layer | Status |
|---|---|
| PostgreSQL schema (`lib/db`) | Untouched |
| Express API (`artifacts/api-server`) | Untouched |
| Workbook importer, dry-run/token/commit | Untouched |
| Lifecycle (Published/Draft/Archived), draft snapshots, row locking | Untouched |
| Admin editor (`Admin.tsx`, 1,390 lines) | Untouched — stays a Vite SPA |
| Redirects table and `/api/redirects/lookup` | Untouched — consumed, not modified |
| `public-v2.css`, `styles.css`, all design tokens | **Copied byte-for-byte** |

**Why the design survives:** the design is not in the React components, it is in the CSS. Components emit class names; `public-v2.css` does all the looking. Copy the stylesheets unchanged and reproduce the same DOM and class names, and the result is pixel-identical by construction — not by careful eyeballing.

## 1. Target architecture

One Replit autoscale deployment, two processes:

```
Replit autoscale deployment  (single start command)
│
├── Next.js          listening on $PORT        ← public front door
│     /                        Home
│     /products                Directory
│     /products/[category]     Category            (11)
│     /products/[category]/[subcategory]           (45)   ← NEW
│     /product/[slug]          Product detail      (150)
│     /about /contact /guide /resources /availability
│     /sitemap.xml  /robots.txt
│     middleware.ts            301 redirect lookup
│
│     rewrites:  /api/*   →  http://localhost:5001/api/*
│                /admin/* →  http://localhost:5001/admin/*
│
└── Express          listening on :5001        ← unchanged backend
      /api/*                   existing API
      /admin/*                 serves the existing Vite admin build
```

### Two rules that this architecture exists to protect

1. **Next fetches from the public API over HTTP. It must never query `lib/db` directly.**
   The Express API builds a public field whitelist as a deliberate safety boundary. Querying Drizzle directly from a server component bypasses that whitelist and would risk leaking breeder names, supplier identity, internal notes, price-list calculations and draft data into server-rendered HTML — where crawlers would index it permanently. The HTTP hop is localhost and costs nothing meaningful.

2. **The admin keeps running exactly as it does today**, served by Express from the existing Vite build. Set `BASE_PATH=/admin` when building it — `vite.config.ts` already reads that env var (`base: process.env.BASE_PATH || '/'`), so no code change is needed.

## 3. Rendering strategy — and why not build-time prerendering

**Use on-demand rendering with cached fetches. Do not use `generateStaticParams` initially.**

The obvious approach is prerendering all ~206 dynamic pages (150 products + 11 categories + 45 sub-categories) at build time. Avoid that here for two reasons:

- Replit's build resources are constrained, and Next.js building 200+ pages is a documented out-of-memory risk. A build that OOMs is an expensive, confusing failure to debug.
- Prerendered pages go stale the moment someone publishes a product, so you would then have to wire a rebuild trigger into the admin's Publish action — extra plumbing, extra cost.

Instead: each page renders on first request and the result is cached. Set the revalidate window on the fetch:

```ts
const res = await fetch(`${API_BASE}/api/products`, {
  next: { revalidate: 300 }   // 5 minutes
});
```

Crawlers receive complete HTML — which is the entire point — the server does almost no repeat work, and published changes appear within five minutes with no rebuild. If you later want build-time prerendering, add `generateStaticParams` as an optimisation once everything else is proven.

**Set `API_BASE` from an env var** (e.g. `http://localhost:5001`). The generated API client hard-codes relative `/api/...` paths, which do not resolve inside a Node server component — this is the one piece of plumbing that genuinely must change.

### Stage 5 — Product detail (the hard one)

This is the only genuinely fiddly file. All of the site's existing SEO lives here, and all of it is currently imperative and client-side:

```js
document.title = `${product.details?.seoTitle || product.name} | IH Seeds`;
document.querySelector('meta[name="description"]').setAttribute("content", ...);
// canonical <link> created and appended to document.head
<script type="application/ld+json" dangerouslySetInnerHTML={...} />
```

The JSON-LD's `additionalProperty` array is derived from `quickFacts` — a ~65-line block with roughly 15 category-conditional branches (Ryegrasses, Fescues, Clovers, Serradellas & Medics, Lucerne, Sub-Tropical, Forage & Grain, Biologicals). That block also renders the visible sidebar. **Extracting it is the crux of this stage.**

```
[HARD RULES BLOCK]

Port pages/ProductDetail.tsx to app/product/[slug]/page.tsx. Markup verbatim.

STEP 1 — Extract, do not rewrite. Move the quickFacts derivation block out of
the component into lib/quickFacts.ts as a PURE function:
    getQuickFacts(product): { label: string, value: string }[]
Change none of its logic or branch order. Both the page body and the metadata
generator will call it. Verify the visible Quick facts card is byte-identical
before continuing.

STEP 2 — Data. Fetch this ONE product server-side. Today the page fetches all
150 products and .find()s one; do not carry that across. If no by-slug endpoint
exists, fetch the list server-side and find it there — but do not fetch it in
the browser.

STEP 3 — 404 and redirects. The current client-side flow (fetch
/api/redirects/lookup then navigate()) becomes: server-side lookup, then a real
redirect or notFound() before anything renders. Delete the redirectLookup
useState and its effect entirely.

STEP 4 — Metadata. Replace the document.title / meta / canonical mutations with
generateMetadata(), including alternates.canonical and openGraph. Delete the
useEffect.

STEP 5 — JSON-LD. Keep the same Product JSON-LD, built from getQuickFacts(), but
rendered by the server component so it is in the raw HTML. Add:
  - offers with availability derived from the default sale line
    (InStock / OutOfStock). Do NOT invent a price.
  - sku from the default sale line's stock code
  - BreadcrumbList
Google's product snippet requires name plus ONE of review / aggregateRating /
offers, so offers-with-availability and no price is valid and correct here —
IH Seeds sells through resellers, so merchant listings do not apply.

The <details> accordions stay native HTML. There should be almost no client
JavaScript left on this page.
```

**Acceptance:**
- Zero-difference diff on at least 8 product pages spanning different categories (a ryegrass, a clover, a serradella, a lucerne, a Mix, a forage crop, a biological, a herb) — the category branches in `quickFacts` are the risk
- `curl` shows the product's own title, meta description, canonical and JSON-LD in raw HTML
- The JSON-LD validates in Google's Rich Results Test
- An old redirected URL returns a real 301 to the right target

### Stage 8 — Workbook SEO fill (run in parallel, from Stage 0)

This is independent of the code and can start immediately. It is also where most of your actual ranking outcome is decided.

Rework `7 Website SEO` in *IH Seeds - Product Data Workbook (pre-filled) - descriptions cleaned.xlsx*:

1. **Re-scope from 79 rows to 150 — one row per product.** Today 73 products have no SEO row, and under the compulsory-SEO publish rule they can never go live. This is the single biggest content blocker.
2. **Add a `seo_title` column** (the sheet has none — the importer currently falls back to `menu_label`, which is nav labels averaging 16 characters). 3. **Rewrite all 79 meta descriptions** to 140–155 chars. They are currently scraped body copy — median 182 chars, 51 of 79 over 160.
4. **Add:** `image_alt`, `og_image`, `canonical_override`, `noindex`, `search_synonyms` (the Fran2o / Biserrulu / Misson misspellings), plus `seo_status`, `title_chars`, `desc_chars` for QA.

6. **New sheet `9 Redirects`** — `old_path`, `new_path`, `status_code`, `reason`, `verified_date`. Exports currently do not include redirects, so the register lives nowhere.
7. **Ask Replit for a deterministic SEO waterfall:** `7.seo_title` → `1 Products.seo_title` → `menu_label` → auto-generated. `1 Products` already has all 150 seo_titles and the importer ignores them; the waterfall unblocks those 73 products immediately.

**Also map, not just the category pages:** `/pasture-seed-guide/`, `/current-availability-of-our-seeds/`, `/rainfall-map/`, `/research-site/`, `/news/`, `/articles/`, `/publications/`, `/about-us/`, `/contact/`, `/products-and-services/`, `/terms-and-conditions/`, `/privacy/`. **Cutover sequence:**

1. Deploy the new site on the Replit URL and leave it there for a week. Crawl it with Screaming Frog (free to 500 URLs) and fix everything it flags.
2. Lower the DNS TTL to 300 seconds, 24 hours ahead.
3. Switch DNS on a **Monday or Tuesday morning** — never a Friday. You want a full working week to react.
4. Immediately after: submit the new sitemap in GSC, request indexing on the top 10 pages, and spot-check 20 old URLs return 301 to the right place.
5. **Week 1:** check GSC Coverage daily for 404s and crawl errors. Some ranking movement is normal — do not panic-change anything in the first fortnight.
6. **Weeks 2–8:** weekly 404 review, compare impressions and clicks against the Stage 0 baseline.
7. Keep the WordPress site backed up and restorable for 90 days.

## Appendix B — Known issues to fix in passing (free wins)

- **Over-fetching.** Every page fetches the whole 150-product catalogue. ProductDetail `.find()`s one from it; Products.tsx pulls all of them purely to `.length` them per card, twice per card inside JSX. Server-side fetching makes this obvious to fix.
- **`AdminCategories.tsx` is dead code** — ~395 lines, never imported. `/admin/products/categories` renders an empty shell today. Decide: wire it up or delete it.
- **`styles.css` ships ~150 lines of `.admin-*` rules** to every public visitor. Split them out — it is invisible and makes the public bundle smaller.
- **Two competing slugify implementations** (`Category.tsx` local vs `useApi.ts`). Unify during Stage 4.
- **`/admin` has no authentication at all.** No login, session, token or 401 handling. Anyone with the URL can publish, archive, delete and export the full catalogue. Deferred by choice — but it is on the Stage 9 gate and must be closed before DNS switches. The minimum viable fix is one middleware check against a password in an env var, roughly 15 minutes, and it can be disabled in development.
